Plan: shared-bot relay for multiple independent JARVIS instances
Goal: one Telegram bot (yours), multiple people each running their own fully independent JARVIS on their own PC (own calendar, own IBKR, own memory), each person's messages routed to their own instance.

Why this needs a relay, restated: a bot token supports exactly one receiver of its traffic. Since nobody's home PC can be that single receiver on everyone else's behalf, something else has to hold that one connection and hand messages off. That something is the relay.

Architecture

Telegram ⇄ [relay: one long-poll connection]
                    │  routing table: chat_id → home_id → live WebSocket
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
  your JARVIS   friend A's    friend B's
  (home PC)     JARVIS        JARVIS
                (their PC)    (their PC)
Each home instance dials out to the relay (WebSocket) — same "no port-forwarding" property your own setup already has, just one hop further out. The relay never runs any tools, sees no calendar/IBKR data beyond what flows through plain-text agent replies, and holds no conversation state of its own — it's a dumb, stateless pipe plus a routing table.

New pieces
1. src/jarvis/relay.py — the relay service (new jarvis-relay entry point)

Long-polls Telegram itself (reuses the polling logic already in telegram_bot.py) — it's the one and only poller, so Telegram's one-consumer limit is never violated.
FastAPI app with one WS /connect endpoint. Each home instance connects, authenticates with a per-home secret token, and the relay marks that home_id as online.
On an incoming Telegram message: look up chat_id → home_id in its config, forward {chat_id, text} down that home's socket if connected; if not connected, reply directly to Telegram ("Your Jarvis is currently offline") — no queueing for v1.
On a reply from a home socket: send it back to the right Telegram chat via sendMessage.
Its own small config file (not config.yaml — this runs somewhere else): the bot token, and a list of {home_id, chat_id, auth_token} — one entry per person you're inviting onto the shared bot. You add entries by hand, same static-list philosophy as allowed_chat_ids today.
2. src/jarvis/relay_client.py — home-side client (new)

Started from server.py's lifespan instead of start_telegram_bot() when a home's config.yaml is in "relay mode" rather than "direct mode" — telegram: gets a mode: direct | relay field; direct is today's behavior, untouched.
Connects out to the relay's wss:// URL, authenticates with its own secret token (relay_auth_token_env, same lazy-env-var pattern as everything else), waits for forwarded messages.
On a message: agent.step() under the same lock as /chat — identical to how telegram_bot.py calls it today, just a different transport getting the text there.
3. Config additions

Each home's config.yaml: telegram.mode: relay, telegram.relay_url, telegram.relay_auth_token_env — replaces bot_token_env/allowed_chat_ids in relay mode (the relay owns Telegram auth and per-chat routing now, not each home).
New relay config file + config/relay.example.yaml template.
.env gains RELAY_AUTH_TOKEN per home; the relay's own .env keeps TELEGRAM_BOT_TOKEN.
Real constraints to decide up front
Hosting the relay: it must be always-on independent of any one person's PC — if it's on your desktop, your friend's bot access dies whenever your PC is off, which defeats the point. Needs a small always-on host (a cheap/free VPS — Fly.io, Oracle free tier, a $5/mo droplet). This is genuinely new infrastructure, not something already in this repo.
TLS: the relay-to-home WebSocket should be wss://, which means the relay host needs a real certificate (most small-VPS setups get this for free via Caddy/Let's Encrypt, or a PaaS that terminates TLS for you) — not optional for anything carrying real conversation content over the public internet.
Trust model, worth saying plainly: as the relay operator, you're the one hop every participant's messages and replies pass through in plaintext to get routed. Nothing is stored, but it's a real trust boundary anyone you invite onto this should know about going in.
Distributing each home's secret token: generated by you, handed to each person over some reasonably secure channel (not committed anywhere) — same handling as any other credential in this project.

Suggested build order:

Relay service, tested solo (you as the only registered home, confirm routing round-trips correctly).
Home-side relay client, tested against that relay from a second machine/VM you control.
Docs for onboarding a real second person (their own config.yaml relay section, their own token, added to your relay's routing list).
Only then actually invite a second real person.
